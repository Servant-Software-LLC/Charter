## Finding 4 — the sample pair could not fail, and the review said it could

| Task | Guardrail | Severity | What slipped through | Fix applied |
|---|---|---|---|---|
| 01 | `guardrails/03-every-test-carries-the-feature-trait.ps1` | **BLOCKER** | The guardrail hardcoded its target path and **ignored `$args[0]`**, so `guardrails samples verify` fed it the `.valid.cs` and `.invalid.cs` samples and it read **neither** — it scanned the (absent) real target both times and exited 1 both times. The committed pair therefore proved nothing: it could not distinguish a correct artifact from the defect it exists to catch. The harness's own words: *"the guardrail may not be reading the sample at all."* | The guardrail is now **dual-mode** — `$args[0]` when present (sample verification), else the real target — with the contract stated in the header so nobody re-hardcodes it. |

**Why round 1 missed it, which is the part worth keeping.** Round 1 *did* smoke-test the pair
two-sided and got the right answers — but it built its own harness: it copied each sample to the
guardrail's hardcoded path in a scratch workspace and ran the script there. That tests the clauses; it
does **not** test the invocation contract, because the real verifier passes the sample as an
**argument** and never moves it. A probe plan built to settle the question recorded exactly that:

```
ARGS: …\tasks\01-probe\samples\01-probe.valid.cs
CWD:  …\scratchpad                     (no GUARDRAILS_* variables set)
```

So the round-1 smoke test was green against a mechanism the harness does not use. The general lesson,
stated so the next pass inherits it: **verifying an artifact against a harness you wrote yourself
proves your harness, not the contract.** When a real verifier exists, run *it*.

This is also the second time in this plan that execution beat reading — and the first time the
*executor* was the harness rather than the review.
